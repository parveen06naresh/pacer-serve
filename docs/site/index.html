The problem

Every batch is a trade between two kinds of user

Continuous batching runs prompt processing (prefill) and token generation (decode) in the same GPU step. Each prompt token you add makes the step slower for everyone already generating. Each one you hold back delays somebody's first token. vLLM and TensorRT-LLM settle this with a fixed token budget per step and a hand-tuned safety margin.

The right budget depends on the model, the accelerator, the SLO and the traffic, and it moves. A roofline analysis of Llama-3-8B puts the free prefill headroom at about 200 tokens on an A100 and about 600 on an L4. At run time, co-tenants and throttling change step latency by tens of percent. A scheduler that packs steps up to its latency prediction is exactly the scheduler that breaks when the prediction goes stale.

How a scheduling step works

Predict, bound, size, order. Every few milliseconds.

1 · predict

Physics-shaped latency model

Seven features with physical units: GEMM tokens, prefill attention FLOPs, decode KV bytes, padding, per-sequence cost. Non-negative least squares. 7.3% error, and 4.4% on step sizes it never saw.

2 · bound

Online conformal risk control

After each step it records actual ÷ predicted and updates its bound with adaptive conformal inference. The long-run miss rate converges to 10% for any sequence of ratios, drift included.

3 · size

Model-predictive budget

Binary search for the largest prompt chunk whose bounded latency still meets the time-per-token SLO. A dot product per probe, microseconds per decision.

4 · order

Moore-Hodgson queueing

The exact algorithm for minimising missed deadlines on one machine decides which prompts to serve first. Hopeless prompts wait, so savable ones make it.

bound: α(t+1) = α(t) + γ · (α − 1[actual/predicted > q(t)]) budget: max c such that q(t) · predicted_latency(decodes + chunks(c)) ≤ SLO_tpot

What didn't work

A clever scheduler without calibration is a liability

Pacer with offline calibration had the best steady-state capacity and the worst result under drift: 37.6%, below every static baseline. It fills each step right up to the bound it believes, so once the machine slows, every step overshoots. Static budgets survive by accident, because they leave slack nobody planned. Online calibration is what turns the model-predictive idea from fragile into robust.

Spending banked time-per-token slack on larger prompt chunks never helped across six scenarios and sometimes hurt, so it is off by default and reported as a negative result.

Scope

What was measured, and what wasn't

  • Measured on a 4-core cloud CPU with a 63M-parameter Llama-architecture model. The prefill and decode cost structure matches GPUs; absolute numbers do not transfer.
  • GPU figures are roofline projections. A Colab notebook reruns the profile and the benchmark on an NVIDIA T4 with one command.
  • The guarantee is per step. Its effect on per-request SLOs is measured, not proven.
  • The paged engine is tested token-exact against a dense full-recompute reference, under irregular chunking and mixed batches.
